## 1. المصادقة والجلسة

### الأدوار الثلاثة وآلية الدخول (نظرة عامة)

النظام يحوي **ثلاثة أنواع مستخدمين** لكن **شاشتي دخول** فقط:

| الدور | شاشة الدخول | طريقة التحقق | الوجهة بعد الدخول | تتبّع الحضور |
|------|--------------|--------------|--------------------|--------------|
| **Admin (مدير المنصة)** | `/Security/AdminLogin` (شاشة منفصلة) | `UserAccountVM.LoginAdmin` | `/Admin/Company` | لا |
| **Company / Supervisor (مشرف الشركة)** | `/Security/Login` (مشتركة) | `UserAccountVM.LoginETask` ثم `isCompany=true` | `/Company/DashBoard` | لا |
| **Employee (موظف)** | `/Security/Login` (مشتركة) | `UserAccountVM.LoginETask` ثم `isCompany=false` | `/Employee/DashBoardEmp` | **نعم** (يبدأ Heartbeat كل 60s) |

**ملاحظة جوهرية:** نموذج الدخول واحد للشركة والموظف؛ النظام يقرّر الوجهة من علم `MvcApplication.userData.isCompany` بعد نجاح التحقق. أما الـ Admin فله نموذج منفصل تمامًا.

### US-AUTH-00 · توجيه الدخول حسب الدور (Login Routing)
**بوصفي** نظامًا، **أرغب** بتوجيه المستخدم تلقائيًا للوحة الصحيحة بعد نجاح الدخول.
**معايير القبول:**
- `/Security/Login` يقبل أي حساب Company أو Employee.
- بعد `LoginETask` ينجح: يُقرأ `MvcApplication.userData.isCompany`:
  - `true` → Redirect `/Company/DashBoard`.
  - `false` → Redirect `/Employee/DashBoardEmp` + تفعيل تتبّع الحضور.
- إذا كان `returnUrl` يحتوي على `/company` لكن المستخدم موظف (أو العكس) — يُمسح `returnUrl` لمنع وصول غير مصرّح.
- `/Security/Login` إذا اكتُشف `returnUrl == /Admin/Company` يُعاد التوجيه إلى `/Security/AdminLogin`.
- أي مستخدم لديه جلسة نشطة يفتح صفحة الدخول → يُحوَّل تلقائيًا للوحته دون إعادة تسجيل.

### US-AUTH-01 · تسجيل دخول المشرف (Company)
**بوصفي** مشرفًا للشركة، **أرغب** بتسجيل الدخول من `/Security/Login` **لكي** أصل إلى لوحة تحكم الشركة.
**معايير القبول:**
- نموذج موحّد مع الموظف (نفس الصفحة) — التمييز عبر بيانات الحساب لا عبر شاشة منفصلة.
- التحقق عبر `UserAccountVM.LoginETask(UserName, Password)`.
- عند النجاح: `isCompany == true` → Redirect `/Company/DashBoard`، وتُحفظ بيانات المستخدم في `MvcApplication.userData`، ويُسجَّل الحدث في `Generallog.LoginORLogout(Login)`.
- عند فشل التطابق: ModelError بالرسالة «اسم مستخدم أو كلمة مرور غير صحيحة».
- الحقول مطلوبة؛ ترك أيٍّ منها فارغًا يعرض رسالة تحقق.
- الحساب الموقوف (Stopped) → صفحة `Security/StopedUser`.
- **لا يبدأ تتبّع الحضور** لحساب الشركة.

### US-AUTH-02 · تسجيل دخول الموظف (Employee)
**بوصفي** موظفًا، **أرغب** بتسجيل الدخول من نفس صفحة `/Security/Login` **لكي** أرى مهامي ويُسجَّل حضوري تلقائيًا.
**معايير القبول:**
- نفس نموذج المشرف (شاشة موحّدة).
- بعد `LoginETask` ينجح و`isCompany == false`: Redirect `/Employee/DashBoardEmp`.
- **يُفعَّل علم الجلسة** ويبدأ تسجيل الحضور التلقائي + Heartbeat كل 60 ثانية (انظر [US-ATN-01](#us-atn-01--تسجيل-الحضور-تلقائيا)).
- الحساب الموقوف → نفس صفحة الإيقاف.

### US-AUTH-03 · تسجيل دخول مدير النظام (Admin)
**بوصفي** مدير منصة، **أرغب** بتسجيل الدخول من شاشة منفصلة تمامًا **لكي** أدير الشركات المسجَّلة.
**معايير القبول:**
- صفحة مستقلة `/Security/AdminLogin`.
- التحقق عبر `UserAccountVM.LoginAdmin(UserName, Password)` (دالة مختلفة عن LoginETask).
- عند النجاح → Redirect `/Admin/Company`.
- خروج Admin عبر `/Security/AdminLogout` (مسار مستقل).
- إذا حاول Admin الدخول من `/Security/Login` لن يُعتبر مصرَّحًا.

### US-AUTH-04 · تسجيل الخروج
**بوصفي** أي مستخدم، **أرغب** بإنهاء الجلسة **لكي** أحمي حسابي.
**معايير القبول:**
- زر «تسجيل الخروج» يستدعي `/Security/Logout`.
- **للموظف**: يتم استدعاء `Checkout()` لتسجيل وقت الانصراف قبل مسح الجلسة.
- **للمشرف**: لا يوجد Checkout — تُمسح الكوكيز والجلسة فقط.
- بعد النجاح يُحوَّل المستخدم إلى صفحة الدخول.

### US-AUTH-05 · نسيت كلمة المرور
**بوصفي** مستخدمًا نسيتُ كلمتي، **أرغب** بإدخال بريدي **لكي** أستعيد الوصول.
**معايير القبول:**
- صفحة `/Security/ForgetPasswoed` بحقل بريد إلكتروني واحد.
- إذا كان البريد مسجَّلًا تُرسل رسالة استعادة وتظهر شاشة تأكيد.
- إذا غير مسجَّل تظهر رسالة خطأ مناسبة (دون كشف وجود/عدم وجود الحساب لأسباب أمنية).

### US-AUTH-06 · تغيير كلمة المرور
**بوصفي** مستخدمًا داخل النظام، **أرغب** بتغيير كلمتي **لكي** أرفع مستوى الأمان.
**معايير القبول:**
- نموذج يطلب: القديمة، الجديدة، تأكيد الجديدة.
- يجب أن تطابق القديمة كلمة المرور الحالية.
- يجب أن تتطابق الجديدة مع التأكيد.
- عند الفشل تظهر رسالة محددة لكل حقل.

### US-AUTH-07 · حماية المسارات
**بوصفي** نظامًا، **أرغب** بمنع الوصول لأي صفحة محمية بدون جلسة.
**معايير القبول:**
- أي طلب يجد `HttpContext.Session["User"] == null` يُحوَّل إلى `/Security/Login`.
- المعاملات الحساسة (TaskDetails، TaskExtensions، AddEdit) تستخدم `[EncryptedActionParameter]` لمنع التلاعب بالـ ID في الرابط.
- المتصفحات المدعومة: Chrome، Edge بشكل كامل؛ Firefox/Safari تجريبيًا؛ IE غير مدعوم.

## 2. مدير المنصة — Admin

> **النطاق الفعلي للـ Admin في الكود:** منطقة `Areas/Admin` تضم Controllers اثنين فقط: `CompanyController` و`EmployeeController`. لا توجد تقارير مخصّصة للـ Admin في هذه المنطقة — التقارير التشغيلية للمهام/المشاريع/الإنتاجية تخصّ منطقة الشركة. Admin يعمل على مستوى **المنصة** (تسجيل الشركات وموظفيها)، وليس على مستوى المهام.

### إدارة الشركات (Admin → Company)

#### US-ADMIN-CO-01 · عرض قائمة الشركات
**بوصفي** Admin، **أرغب** بعرض جميع الشركات المسجَّلة على المنصة.
**معايير القبول (`/Admin/Company/Index`):**
- جدول الشركات يعرض: الاسم، البريد، السجل التجاري، الحالة (نشط/موقوف).
- مصدر البيانات: `CompanyVM().Select()` بدون فلاتر.

#### US-ADMIN-CO-02 · البحث والفلترة في الشركات
**بوصفي** Admin، **أرغب** بفلترة الشركات بمعايير متعددة.
**معايير القبول (`/Admin/Company/Search`):**
- فلاتر: الاسم، البريد، السجل التجاري، الحالة (`IsActive`: 1=نشط، 2=موقوف، فارغ=الكل).
- يُرجع PartialView `_Index.cshtml` (تحميل جزئي بدون إعادة تحميل الصفحة).

#### US-ADMIN-CO-03 · إضافة شركة جديدة
**بوصفي** Admin، **أرغب** بتسجيل شركة جديدة على المنصة.
**معايير القبول (`/Admin/Company/AddEdit` بدون Id):**
- الحقول المتوقعة في `CompanyVM`: الاسم، البريد، السجل التجاري، بيانات التواصل، شعار/مرفق.
- التحقق الفوري من التكرار قبل الحفظ:
  - **الاسم** عبر `CheckDublicateName`.
  - **البريد** عبر `CheckDublicateEmail`.
  - **السجل التجاري** عبر `CheckDublicateCommercialRegister`.
- عند الحفظ: استدعاء `company.Save()` ثم Redirect إلى `Index`.

#### US-ADMIN-CO-04 · تعديل بيانات شركة
**بوصفي** Admin، **أرغب** بتعديل أي بيانات شركة قائمة.
**معايير القبول (`/Admin/Company/AddEdit?Id=…` — معامل مشفّر `[EncryptedActionParameter]`):**
- يُحمَّل النموذج عبر `CompanyVM().Details(Id)`؛ إذا كان `Id` غير صالح يعود إلى `Index`.
- نفس قواعد التكرار من US-ADMIN-CO-03 — لكن مع تجاوز السجل الحالي.
- يُحفظ التعديل عبر نفس `Save()`.

#### US-ADMIN-CO-05 · عرض تفاصيل شركة
**بوصفي** Admin، **أرغب** بمشاهدة بطاقة تفاصيل شركة.
**معايير القبول (`/Admin/Company/Details?Id=…`):**
- `Id` مشفّر.
- يعرض الشاشة بقراءة فقط؛ إذا الشركة غير موجودة → Redirect لـ Index.

#### US-ADMIN-CO-06 · حذف شركة
**بوصفي** Admin، **أرغب** بحذف شركة من المنصة.
**معايير القبول (`/Admin/Company/Delete` — POST):**
- يستقبل `Id` و `CurrenClass` (الكلاس للمصادر).
- يستدعي `CompanyVM().Delete(Id)`.
- يُرجع Boolean (نجاح/فشل).
- ⚠️ هذا حذف منطقي (`IsDeleted=true` على الأرجح) لأن US-ADMIN-EMP-08 يعتمد على «إعادة توظيف موظف محذوف».

#### US-ADMIN-CO-07 · تفعيل/إيقاف شركة
**بوصفي** Admin، **أرغب** بإيقاف شركة دون حذفها (مثل تعليق اشتراك).
**معايير القبول (`/Admin/Company/SetIsActive` — POST):**
- يقلب علم `IsActive` للشركة.
- الشركة الموقوفة: موظفوها يُمنعون من تسجيل الدخول (يُحوّلون لـ StopedUser).

#### US-ADMIN-CO-08 · تنزيل ملف شركة
**بوصفي** Admin، **أرغب** بتنزيل مرفق مرتبط بشركة (شعار/مستند).
**معايير القبول:** `/Admin/Company/DownloadFile` يُرجع الملف من مسار `/Upload/Task/`.

### إدارة الموظفين على مستوى المنصة (Admin → Employee)

> Admin يستطيع إدارة موظفي **أي شركة**، بينما المشرف (Company) يدير موظفي شركته فقط.

#### US-ADMIN-EMP-01 · عرض جميع موظفي المنصة
**بوصفي** Admin، **أرغب** برؤية كل الموظفين عبر جميع الشركات.
**معايير القبول (`/Admin/Employee/Index`):**
- جدول الموظفين يعرض: الاسم، الشركة، البريد، المسمى الوظيفي، الحالة.
- لا قيود على الشركة (بخلاف منطقة الشركة).

#### US-ADMIN-EMP-02 · البحث والفلترة في الموظفين
**بوصفي** Admin، **أرغب** بفلترة الموظفين عبر الشركات.
**معايير القبول (`/Admin/Employee/Search` — POST):**
- فلاتر: الاسم، اسم الشركة، المسمى الوظيفي، البريد، الحالة (1=نشط، 2=موقوف).
- يُرجع PartialView `_Index.cshtml`.

#### US-ADMIN-EMP-03 · إضافة موظف لأي شركة
**بوصفي** Admin، **أرغب** بإضافة موظف جديد وربطه بشركة محدّدة.
**معايير القبول (`/Admin/Employee/AddEdit` بدون id):**
- قائمة منسدلة بـ **الشركات النشطة فقط** (`GetActiveCompanies`).
- الحقول الإلزامية: الاسم، البريد، الجوال، الهوية، الجنس، تاريخ الميلاد، CompanyID.
- ميكانيكية reCAPTCHA معدّة في الكود لكن معطّلة حاليًا (مُعلَّقة).
- التحقق من التكرار:
  - **الاسم** داخل نطاق الشركة (`CheckDuplicate` يقبل `companyID`).
  - **البريد** داخل الشركة (`CheckDuplicateEmail` / `CheckEmployeeDuplicateEmail`).
  - **الجوال** على مستوى الشركة الحالية (`CheckDuplicateMobile`).
  - **الهوية** على مستوى الشركة (`CheckDuplicateNationID`).
  - **رقم تسلسلي/مكتب العمل** فريد (`CheckForUniquSequenceNumberLaborOfficeID`).
- التحقق من تاريخ الميلاد: ليس في المستقبل (`ValidateDateLessThanToday` — يدعم هجري وميلادي وفق `MvcApplication.IsGregDate`).
- رفع صورة شخصية: `AddImage` يحفظ في `/Upload/Employee/` ويُرجع المسار، أو `UploadError` عند الفشل.
- بعد الحفظ Redirect لـ `Index`.

#### US-ADMIN-EMP-04 · تعديل بيانات أي موظف
**بوصفي** Admin، **أرغب** بتعديل بيانات أي موظف في أي شركة.
**معايير القبول (`/Admin/Employee/AddEdit?id=…` — معامل مشفّر):**
- يُحمَّل عبر `EmployeeDetails(id)` مع تعبئة `ViewBag.Company` بالشركة الحالية للموظف.
- نفس قواعد التحقق من التكرار مع تجاوز سجل الموظف الحالي.

#### US-ADMIN-EMP-05 · تفعيل/إيقاف موظف
**بوصفي** Admin، **أرغب** بإيقاف موظف عبر زر سريع.
**معايير القبول (`/Admin/Employee/SetIsActive` — POST):** يقلب علم النشاط للموظف؛ الموقوف يُمنع من الدخول.

#### US-ADMIN-EMP-06 · حذف موظف
**بوصفي** Admin، **أرغب** بحذف موظف نهائيًا من قائمة الشركة.
**ملاحظة من الكود:** دالة `Delete` على EmployeeController مُعلَّقة في هذا الإصدار؛ الحذف الفعلي يتم عبر CompanyController أو دالة موروثة من `BaseAdminController.Delete(int Id, string CurrenClass)` لأن `CompanyController.Delete` يَبني عليها وقد تكون الموظف يستخدم نفس الواجهة المرفوعة.
**معايير القبول:** عند تفعيل الحذف يصبح حذفًا منطقيًا (يُظهر السجل لإعادة التوظيف لاحقًا — US-ADMIN-EMP-08).

#### US-ADMIN-EMP-07 · فحص هوية موظف محذوف
**بوصفي** Admin، **أرغب** بمعرفة هل رقم الهوية يخص موظفًا محذوفًا سابقًا في نفس الشركة.
**معايير القبول (`/Admin/Employee/CheckDeletedEmpNationlID` — POST):** يُرجع نتيجة تشير لإمكانية إعادة التوظيف.

#### US-ADMIN-EMP-08 · إعادة توظيف موظف محذوف
**بوصفي** Admin، **أرغب** بإعادة تفعيل موظف محذوف بنفس البيانات.
**معايير القبول (`/Admin/Employee/RehireDeletedEmp` — POST):** يستدعي `UpdateRehireDeletedEmployee(EmpId)` فيستعيد السجل بدل إنشاء جديد.

#### US-ADMIN-EMP-09 · رفع صورة موظف
**بوصفي** Admin، **أرغب** برفع صورة شخصية للموظف.
**معايير القبول (`/Admin/Employee/AddImage` — POST):**
- يستخدم `UploadFile().Uploadfile` مع نفس قواعد رفع الملفات (الامتداد، الحجم، MIME).
- يُحفظ في `/Upload/Employee/`.

### تقارير Admin (Platform Reports)

> **تصحيح:** Admin **يملك ثلاثة تقارير** يصل لها من قائمة جانبية تظهر فقط لحسابات Admin. التقارير غير مستضافة تحت `Areas/Admin` لكن Controllers الخاصة بها على المسار الجذر، وتستخدم نفس البنية (Provider → Companies → Employees) للفلترة عبر المنصة كلها.

#### US-ADMIN-RPT-01 · تقرير الحضور والانصراف
**بوصفي** Admin، **أرغب** بمراجعة حضور موظفي أي شركة على المنصة خلال فترة معيّنة.
**معايير القبول (`/Attendance/AttendanceReport` ← Controller: `AttendanceController`):**
- شاشة فلترة:
  - **مزوّد الخدمة** (Provider) — قائمة منسدلة من `SharedService.GetProviders()`.
  - **الشركة** — تُحمَّل عبر AJAX `/Attendance/GetCompanies` فور اختيار المزوّد.
  - **الموظف** — يُحمَّل عبر AJAX `/Attendance/GetEmployees` فور اختيار الشركة (اختياري؛ تركه فارغًا = كل الموظفين).
  - **السنة** + **الشهر** — السنوات آخر 5 (تنازليًا)؛ الأشهر تُحمَّل عبر `/Attendance/GetMonths` ولا تتجاوز الشهر الحالي للسنة الحالية.
  - **نطاق تاريخ مخصّص** (FromDate, ToDate) كصيغة `dd/MM/yyyy`.
  - **نوع التقويم** `calendarType`: 0 = هجري، 1 = ميلادي.
- زر «استخراج التقرير» يُرسل لـ `/Attendance/ViewReport` ثم Redirect إلى `/Reports/Attendance` لتشغيل `Attendance.rdlc`.
- **سلوك التواريخ:** عند `calendarType=0` تُحوَّل التواريخ هجري→ميلادي عبر `QvLib.QVUtil.Date.hijritodate` قبل تمريرها لـ `sp_Attendance`.
- **عرض البيانات:**
  - `AttendanceDate` يُعرض بتنسيق التقويم المختار.
  - `CheckInTime` و `CheckOutTime` تُحوَّل من 24 ساعة إلى **12 ساعة بدون AM/PM** (مثل: `08:30`، `04:15`).
- **معاملات التقرير:** `StartDate`, `EndDate`, `ReportPeriod` (مثل "شهر يناير 2026")، `CalendarType`.
- **حالة فراغ:** إذا لم تُرجع `sp_Attendance` بيانات → التقرير يفتح فارغًا (لا رسالة خطأ في الشاشة).
- **معاملة فلتر `companyId` في URL:** إذا فُتحت الصفحة بـ `?companyId=N` يختفي فلتر المزوّد والشركة (Layout مختلف `_LayoutNoSearch`) ويُثبَّت companyId كـ hidden.

#### US-ADMIN-RPT-02 · تقرير أداء الموظفين
**بوصفي** Admin، **أرغب** بمعرفة إنتاجية موظفي شركة محدّدة خلال فترة.
**معايير القبول (`/EmployeePerformanceReport` ← Controller: `EmployeePerformanceReportController`):**
- شاشة الفلترة:
  - **مزوّد الخدمة** ثم **الشركة** (cascade مثل تقرير الحضور، عبر `/EmployeePerformanceReport/GetCompanies`).
  - **CompanyId** — مطلوب.
  - **FromDate / ToDate** — اختياريان، صيغة `dd/MM/yyyy`.
- عند الإرسال POST يستدعي `sp_EmployeePerformanceReport(@CompanyId, @PeriodStart, @PeriodEnd)`.
- إذا لم توجد بيانات: يُعاد عرض الشاشة برسالة **"لا يوجد بيانات"** + إعادة تعبئة قائمة الشركات.
- عند وجود بيانات: Redirect إلى `/Reports/EmployeePerformance` لتشغيل `EmployeePerformance.rdlc`.
- البيانات المعروضة (من الستورد): مقاييس أداء كل موظف خلال الفترة (عدد المهام، المهام المنجزة، المتأخرة، نسبة الإنجاز — استنادًا لأعمدة `sp_EmployeePerformanceReport_Result`).
- **القيود:** التقرير لشركة واحدة فقط في كل تشغيل — لا يدعم Admin استخراج أداء عابر للشركات في تشغيل واحد.

#### US-ADMIN-RPT-03 · تقرير الموظفين (قائمة بيانات)
**بوصفي** Admin، **أرغب** بقائمة شاملة بموظفي شركة محدّدة (بيانات تعريفية، لا أداء).
**معايير القبول (`/EmployeesReport` ← Controller: `EmployeesReportController`):**
- شاشة الفلترة:
  - **مزوّد الخدمة** → **الشركة** (cascade عبر `/EmployeesReport/GetCompanies`).
  - **CompanyId** — مطلوب.
  - **لا يوجد فلتر تاريخ** (التقرير هو قائمة موظفين، ليس تقرير فترة).
- زر الاستخراج يُرسل GET إلى `/EmployeesReport/ViewReport?CompanyId=N`.
- يستدعي خدمة البيانات ثم Redirect إلى `/Reports/Report3` لتشغيل `EmployeesReport.rdlc` (يُحمَّل بـ DataSource `DS_EmpReport`).
- التقرير يعرض بيانات الموظفين (الاسم، البريد، الجوال، المسمى، تاريخ التوظيف، الحالة …) — تفاصيل البيانات الفعلية مرتبطة بـ stored procedure للموظفين.

### آلية الـ Cascade للفلترة (مشترك بين التقارير الثلاثة)
**بوصفي** نظامًا، **أرغب** بربط القوائم المنسدلة:
1. Admin يختار **Provider** → AJAX تستدعي endpoint `GetCompanies(provider)` (يختلف controller حسب التقرير لكن المنطق واحد عبر `SharedService.GetCompaniesByproviderId`).
2. عند اختيار **Company** → AJAX تستدعي `GetEmployees(companyId)` (تقرير الحضور فقط؛ التقريران الآخران لا يفلتران بالموظف).
3. القيمة الافتراضية لكل قائمة: «الكل».
4. الشركات المعروضة في `EmployeePerformanceReportService.GetCompanies` و`AttendanceReportService.GetCompanies` تُفلتر بـ `IsDeleted == false` (لا يظهر الشركات المحذوفة).

### الحدود الواضحة في صلاحيات الـ Admin

| الميزة | يستطيع Admin؟ | الملاحظة |
|--------|:----:|---------|
| إنشاء/تعديل/حذف الشركات | نعم | فقط Admin يستطيع |
| تفعيل/إيقاف الشركات | نعم | فقط Admin |
| إضافة موظف لأي شركة | نعم | المشرف يضيف لشركته فقط |
| **تقرير الحضور (متعدد الشركات)** | **نعم** | US-ADMIN-RPT-01 |
| **تقرير أداء الموظفين** | **نعم** | US-ADMIN-RPT-02 |
| **تقرير الموظفين (بيانات)** | **نعم** | US-ADMIN-RPT-03 |
| إنشاء/تعديل المهام | **لا** | منطقة المهام للشركة فقط |
| تقارير المهام/المشاريع | **لا** | تقارير المهام TaskReport/ProjectReport للشركة فقط |
| إعداد المهام المتكررة | **لا** | للشركة فقط |
| رؤية سجل العمليات | **لا** | للشركة فقط (`/Log/*`) |
| المساعد الذكي | **لا يظهر** | للموظفين فقط |

> **خلاصة:** صلاحية Admin = إدارة المنصة (شركات + موظفين) + **ثلاثة تقارير مستوى منصة** (حضور، أداء، قائمة موظفين). تقارير المهام/المشاريع/الإحصائيات البيانية تخص دور الشركة (انظر القسم 9).

## 5. دورة حياة المهمة

### US-TASK-01 · إنشاء مهمة جديدة
**بوصفي** مشرفًا، **أرغب** بإنشاء مهمة وإسنادها إلى موظف أو أكثر.
**معايير القبول (`/Company/Task/SaveData`):**
- الحقول المطلوبة: العنوان، الموظف (واحد على الأقل)، تاريخ البداية، تاريخ النهاية، المدة، الأولوية.
- العنوان فريد داخل الشركة (`checkDublicated`).
- تاريخ البداية ≥ اليوم، النهاية > البداية (`CheckDate`).
- المدة تتوافق مع أيام العمل بعد استثناء العطل والإجازات (`DateDifference` يحسب بناءً على `WeekEndDisplayVM` و`HolidayDisplayVM`).
- يمكن رفع مرفقات (انظر [المرفقات](#5-التعليقات-والمرفقات)).
- عند الإسناد لعدة موظفين: **يُنشأ سجل مهمة منفصل لكل موظف**.
- يتم تسجيل العملية في سجل العمليات.
- يُرسَل إشعار SignalR من نوع `NewTask` للموظف(ين).

### US-TASK-02 · تعديل مهمة
**بوصفي** مشرفًا، **أرغب** بتعديل عنوان/تواريخ/أولوية/مرفقات/مشروع المهمة.
**معايير القبول:** `/Company/Task/EDitTask` يحمّل البيانات، `SaveTask` يحفظ. عند إعادة الإسناد لموظف آخر تنتقل المرفقات معها.

### US-TASK-03 · قبول الموظف للمهمة الجديدة
**بوصفي** موظفًا، **أرغب** بقبول مهمة جديدة **لكي** أبدأ العمل.
**معايير القبول:**
- زر «قبول» يُتاح فقط للحالة «جديدة».
- يستدعي `Employee/Tasks/AcceptTask` وينقل الحالة إلى **Accepted (8)** ثم تلقائيًا إلى **InProgress (2)** إذا كانت `تاريخ البداية ≤ الآن`.
- يُرسل إشعار `AcceptTask` للمشرف.

### US-TASK-04 · رفض الموظف للمهمة الجديدة
**بوصفي** موظفًا، **أرغب** برفض مهمة لا تخصني **لكي** أُعيدها للمشرف.
**معايير القبول:** `RejectTask` يحوّل الحالة إلى **Rejected (9)** ويرسل إشعار للمشرف. لا يمكن للموظف اتخاذ إجراءات أخرى بعد الرفض.

### US-TASK-05 · بدء المهمة (Start)
**بوصفي** موظفًا، **أرغب** ببدء مهمة قبلتُها **لكي** يبدأ احتساب وقت التنفيذ. (`StartTask` ينقلها إلى InProgress).

### US-TASK-06 · إدخال الوقت المستغرق
**بوصفي** موظفًا، **أرغب** بتسجيل عدد ساعات العمل **لكي** يظهر في التقارير.
**معايير القبول:**
- `UpdateTaskDalyTime` للوقت اليومي (عشري).
- `UpdateTaskTime` لإجمالي وقت المهمة.
- الصيغة المقبولة: `H:MM` أو رقم عشري؛ غير ذلك → «صيغة الوقت غير صحيحة».

### US-TASK-07 · إنهاء المهمة من الموظف
**بوصفي** موظفًا، **أرغب** بإنهاء مهمة عند الانتهاء منها.
**معايير القبول:**
- `EmpFinishTask` يُحوّل الحالة من **InProgress** إلى **Done (5)**.
- يُرسل إشعار `EndTask` للمشرف.
- يجب أن يكون الوقت المستغرق مُسجَّلًا.

### US-TASK-08 · قبول المشرف لإنجاز المهمة
**بوصفي** مشرفًا، **أرغب** بقبول مهمة منتهية **لكي** أُغلقها.
**معايير القبول:** `Company/Company/AcceptTask` ينقل الحالة من **Done** إلى **Approved (6)**؛ يُرسل إشعار `Approved` للموظف.

### US-TASK-09 · رفض المشرف لإنجاز المهمة
**بوصفي** مشرفًا، **أرغب** برفض إنجاز ضعيف **لكي** يعيد الموظف العمل.
**معايير القبول:** `RefusedTask` ينقل الحالة إلى **NotApproved (7)** وتعود للموظف للعمل عليها. يُرسل إشعار.

### US-TASK-10 · تعليق المهمة (Pending)
**بوصفي** مشرفًا، **أرغب** بتعليق مهمة مؤقتًا **لكي** أوقف العمل عليها بدون إلغائها.
**معايير القبول:** الحالة تنتقل إلى **Pending (3)**؛ لا يمكن للموظف اتخاذ أي إجراء؛ يستطيع المشرف إلغاء التعليق.

### US-TASK-11 · المهمة المتأخرة (Delay)
**بوصفي** نظامًا، **أرغب** بوسم المهمة كمتأخرة عند تجاوز تاريخ النهاية مع بقائها قابلة للإنهاء.
**معايير القبول:** **Delay (10)** هو علم محسوب وليس انتقالًا نهائيًا — يبقى الموظف قادرًا على الإنهاء؛ يظهر التأخير في التقارير.

### US-TASK-12 · أرشفة المهمة
**بوصفي** مشرفًا، **أرغب** بأرشفة مهام مكتملة **لكي** تختفي من القوائم النشطة.
**معايير القبول:** `Archive` يضع `IsArchived=true`؛ لا تظهر إلا بتفعيل فلتر الأرشيف.

### US-TASK-13 · إعادة إسناد المهمة
**بوصفي** مشرفًا، **أرغب** بنقل مهمة من موظف لآخر دون فقد المرفقات والتعليقات.

### US-TASK-14 · تغيير الأولوية
**بوصفي** مشرفًا، **أرغب** بتغيير أولوية المهمة في أي وقت.
**معايير القبول:** `ChangePriority` يُحدّث الحقل ويُرسل إشعارًا للموظف.

### US-TASK-15 · حذف جماعي للمهام
**بوصفي** مشرفًا، **أرغب** بحذف عدة مهام دفعة واحدة **لكي** أنظّف القائمة.
**معايير القبول:**
- `BulkDelete` يستقبل مصفوفة IDs.
- **القيود:** يُسمح فقط بحذف مهام بحالة «جديدة»، وبحد أقصى **500 مهمة** بعملية واحدة.

### US-TASK-16 · البحث والفلترة في المهام
**بوصفي** أي مستخدم، **أرغب** بفلترة قائمة المهام.
**معايير القبول:** فلاتر العنوان، الحالة، الأولوية، المشروع، تاريخ البداية والنهاية، إظهار/إخفاء المؤرشف، صفحات 10 لكل صفحة.

### US-TASK-17 · حالات المهمة (State Machine)
```
New (1)
  ├─► Accepted (8) ──► InProgress (2) ──► Done (5)
  │                                          ├─► Approved (6)      [نهائي]
  │                                          └─► NotApproved (7) ──► back to InProgress
  └─► Rejected (9)                                                  [نهائي]
       Pending (3) ◄──► InProgress (2)  (يمكن للمشرف التعليق وإلغاؤه)
       Delay (10) — علم محسوب عند تجاوز تاريخ النهاية، لا يمنع الانتقالات
       IsArchived — فلتر مستقل عن الحالة
```

## 10. الحضور والانصراف

### US-ATN-01 · تسجيل الحضور تلقائيًا
**بوصفي** موظفًا، **أرغب** أن يُسجَّل حضوري تلقائيًا فور دخولي **لكي** لا أنسى.
**معايير القبول:**
- يحدث الحضور بعد نجاح تسجيل الدخول مباشرة.
- **لا ينطبق على المشرف ولا Admin** — تتبّع الحضور للموظفين فقط.
- يُضبط `Session["HasActiveAttendance"]=true`.

### US-ATN-02 · النبض كل دقيقة
**بوصفي** نظامًا، **أرغب** بتسجيل آخر نشاط الموظف كل 60 ثانية.
**معايير القبول:**
- JS تُرسل POST لـ `/Attendance/LogActivity` كل 60s.
- تُحدَّث قيمة `LastHeartbeat` في جدول `Attendance`.
- أحداث (click/keypress/mousemove/scroll/touchstart) مفرملة لمرة كل 5 ثوانٍ كحد أقصى.

### US-ATN-03 · تنبيه عدم النشاط
**بوصفي** نظامًا، **أرغب** بإظهار نافذة منبثقة عند ركود الموظف 30 دقيقة.
**معايير القبول:**
- بعد 30 دقيقة بدون نشاط: تظهر نافذة لا يمكن إغلاقها بالنقر خارجها.
- تبدأ بعدّاد تنازلي 02:00 (المذكور في QA docs).
- زرّان: «استمر في العمل» (يعيد ضبط العدّاد) و«إنهاء العمل» (يُسجِّل الانصراف فورًا).
- أحداث الفأرة/الكيبورد خلف النافذة لا تُلغي العدّاد.

### US-ATN-04 · الانصراف التلقائي بعد انتهاء العدّاد
**بوصفي** نظامًا، **أرغب** بتسجيل انصراف الموظف عند انتهاء العدّاد دون استجابة.
**معايير القبول:**
- يُستدعى `/Attendance/InactivityCheckout`.
- وقت الانصراف = آخر `LastHeartbeat` (وليس وقت الانتهاء الفعلي للعدّاد).

### US-ATN-05 · الانصراف عند إغلاق المتصفح
**بوصفي** نظامًا، **أرغب** بتسجيل انصراف عند إغلاق التاب/المتصفح.
**معايير القبول:**
- يستخدم `navigator.sendBeacon` على أحداث `beforeunload` / `pagehide` إلى `/Attendance/BeaconCheckout`.
- يُتخطّى البيكون للروابط الداخلية والنماذج (لتفادي تسجيل انصراف خاطئ عند التنقل).
- Safari قد لا يدعم سلوك sendBeacon بالكامل (محدود).

### US-ATN-06 · الانصراف اليدوي
**بوصفي** موظفًا، **أرغب** بتسجيل خروج صريح **لكي** أنهي يوم العمل.
**معايير القبول:** زر الخروج → يُستدعى `Checkout()` قبل مسح الجلسة.

### US-ATN-07 · تقرير الحضور
**بوصفي** مشرفًا أو موظفًا، **أرغب** بعرض تقرير حضور تفصيلي.
**معايير القبول (`/Attendance/AttendanceReport` → `ViewReport`):**
- فلاتر: الشركة، الموظف، الفترة (شهر/سنة، أو نطاق تواريخ).
- يدعم التقويم الهجري والميلادي عبر معامل `calendarType` (0 هجري، 1 ميلادي).
- التواريخ تُحوَّل هجري→ميلادي قبل الاستعلام من قاعدة البيانات.
- **عرض الوقت 12 ساعة** (نظام صباحًا/مساءً) — تحويل من تخزين 24 ساعة عند العرض.
- يعرض: التاريخ، وقت الحضور، وقت الانصراف، عدد الساعات.

### US-ATN-08 · حالة الحضور الحالية
**بوصفي** نظامًا، **أرغب** بمعرفة هل الموظف لديه جلسة حضور نشطة الآن. (`GetCurrentAttendance` يخدم تتبّع JS).

### US-NTF-01 · إشعار فوري على المهام
**بوصفي** أي مستخدم، **أرغب** بتلقّي إشعارات فورية عند تغيّر مهمة تخصّني.
**معايير القبول:**

| تغيير الأولوية | الموظف | `ChangePriority` |
| إضافة تعليق | جميع المشاركين | `AddComment` |

### US-NTF-04 · ربط معرّف SignalR بالجلسة

### US-NTF-05 · إشعار استعادة كلمة المرور

**معايير القبول:**
- يظهر في **صفحات الموظف فقط**؛ لا يظهر للمشرف ولا للـ Admin.

- يحتوي على 17 سؤالًا سريعًا (أزرار جاهزة).
- الضغط على تبويب يفلتر الأسئلة لفئتها.
- الأسئلة السريعة تُجاب فورًا من ملف Q&A المحلي.
- الأسئلة الحرة تُرسل إلى `/Chat/Send` الذي:
  1. يحاول مطابقة Q&A أولًا.
  2. إذا لم يجد، يستدعي Claude API (`claude-haiku-4-5-20251001` بحد 1024 token).
  3. يُرجع `{ answer, source: "qa"|"ai" }`.
- ملف System Prompt يضمّن دور المستخدم واسمه ومعرّفه، ويقصر الإجابات على نطاق تيلي ساك.
- مفتاح API من إعداد `ClaudeApiKey` في Web.config.

### US-SYS-01 · دعم اللغة العربية و RTL

### US-SYS-09 · المُعرّفات المشفّرة في الروابط
**بوصفي** نظامًا، **أرغب** بتشفير IDs الحساسة في URL (`[EncryptedActionParameter]`) لمنع تلاعب المستخدم بالـIDs.

### US-SYS-10 · حالات الحافة (Edge Cases)
- إغلاق التاب → تسجيل انصراف.
- تابان مفتوحان وتسجيل خروج من واحد → الجلسات الأخرى قد تبقى حتى انتهاء التحقق.
- انقطاع الإنترنت أثناء النبض → النبض القادم يستأنف؛ آخر `LastHeartbeat` يُستخدم في حساب الانصراف التلقائي.
- محاولة حذف جماعي أكبر من 500 → يُحدّ تلقائيًا إلى 500.
- محاولة الموظف رفع ملف على مهمة Done → مرفوض.
